# QeyNox user experience implementation plan

**Goal:** turn a natural-language business objective into a reviewed, evidence-backed deliverable, reusing the existing business core.
**Scope:** UX specification only; no screens, components, backend changes, dependency changes or runtime certification in this task.
**Reviewed:** 2026-11-13, baseline `d4d042e` on `main`.
**Design authority:** [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md), [design-tokens.css](design-tokens.css), [AGENTS.md](../../AGENTS.md). ## 2. Complete journey

1. **State an outcome.** MyDash asks “What result do you need?” with one dominant **Start a mission** action. Accept a goal (5–5,000 characters); derive an editable short title from the entered text to satisfy the existing 3–200-character contract. Optional constraints sit behind “Add constraints”; do not require a company profile or capability selection first. `POST /v1/operations` saves a `DRAFT`; saving is not execution. If creation times out, check recorded missions before resubmitting: creation has no idempotency key.
2. **Clarify with Soul.** Show a concise interpretation, ask only unresolved questions needed for scope, geography, deliverable or constraints, and let the user correct it. Explain any context requested, its purpose and scope; remembering context is a separate opt-in, revocable choice. Preserve answers across return visits only through an authorized persisted contract. Until the pre-execution contract exists, show the saved draft and an explicit clarification-unavailable state; do not invent an attempt ID or simulate a conversation.
3. **Review Pilot's proposed plan and cost.** Present expected deliverable, included/excluded scope, a short step list, data/tool access and assumptions. Expand dependencies, capability versions and limits under “Details”. Reuse the validated plan-creation/revision services once a real structured proposal exists. A `READY` plan is not approved execution. Show the server quote in its currency/minor units, terms and expiry. Separate the configured service price from execution ceiling/reserved/spent amounts and their estimated/provider-reported/unknown origin. There is no implemented cost-estimation API; unavailable pricing is “Cost unavailable” and blocks approval/start, never zero or an invented range. Do not invent an ETA.
4. **Approve explicitly.** One review panel explains scope, price, budget limits and consequential access. “Approve and start” sequences quote acceptance with a stable idempotency key, then `POST /v1/operations/:id/start` with fresh `expectedVersion` and a separate stable key. Refresh canonical state between commands; acceptance alone is not payment or execution. Paid orders remain `PAYMENT_REQUIRED`; only an explicitly authorized free offer can currently pass the commercial gate. A revised plan or expired quote requires a fresh quote and explicit approval. Plan/quote acceptance, tool-action approval and final result review are distinct decisions.
5. **Execute durably.** After start is acknowledged, show “Execution requested”, then observed business progress from the server. `RUNNING` after an outbox write does not prove Hatchet started. Hatchet remains the sole durable executor; Hermes stays behind `EnginePort`, and tools behind ToolBroker. No browser workflow scheduler, fake agent typing, moving percentage or imagined activity.
6. **Follow progress and intervene.** Show the latest meaningful recorded event, completed/total steps, last refresh and one next decision. Poll summary/activity while the page is visible (initial UI target: every 5 seconds), consume `nextCursor`, drain available event pages and deduplicate by sequence; back off on errors and refresh on return. Stop continuous polling for terminal operations. Disconnection preserves the last view with “Updates unavailable”; it does not stop work. Interrupt shows `INTERRUPT_REQUESTED` until confirmed. A pending approval shows purpose, exact scope and expiry; rejecting or approving waits for the subsequent recorded outcome, without assuming continuation. Unknown execution outcomes require reconciliation, never automatic resubmission.
7. **Review and retrieve deliverables.** Open the document reader with objective, findings, recommended next actions, limits, dated citations and unresolved items. `PARTIAL` and `READY_FOR_REVIEW` remain distinct from `DELIVERABLE`. For an eligible result, record the specific `RESULT_REVIEW` approval, then call `/documents/:documentId/deliver`; follow the returned new document ID. Approval alone does not deliver. Export JSON/HTML through the existing API, then request a signed grant. A stored document can be readable while file delivery is blocked. Preserve previous documents, revisions and attempts; a revision or redo explains affected downstream work and requires explicit confirmation before any new execution/cost.

## 3. Screens, navigation and shared components

The following are **proposed frontend routes**, not existing routes. Primary navigation: **MyDash · Missions · Results**. Results contains the **Library/history** view using the same collection and reader. Capabilities and Account/privacy are secondary navigation. Soul appears in mission clarification and context settings; Pilot appears as the mission's next-decision panel. No agent gallery, chat-only home or customer Hatchet console.

| Screen / proposed route | Essential content and action | Dependency |
|---|---|---|
| Access `/login`, controlled `/register` | Minimal identity fields; honest disabled-registration, invalid-session and denied states. Workspace name/locale only as required by registration. | Existing auth contracts; session/public identity gates. Password recovery/MFA are unavailable. |
| MyDash `/mydash` | Cobalt objective intro, available configured capabilities, recent mission list, genuine attention items. Empty state invites the first goal; no metrics strip. | Recent read model; safe capability catalogue gap. |
| Goal and clarification `/missions/new`, then `/missions/:id` | One goal input; saved draft, concise Soul questions, editable scope summary and contextual consent. | Create contract exists; resumable clarification gap. |
| Missions `/missions` | Reuse the mission list; title, capability when known, status, updated date and next action. | Existing limited lists; label loaded subset, no claim of exhaustive history. |
| Mission workspace `/missions/:id` | One page with Plan, Progress and Results sections, quote/approval panel, Pilot next action and advanced history. Do not build separate plan/monitoring apps. | Existing writes, summaries and polling; detail reads and proposal/cost gaps. |
| Result reader `/missions/:id/results/:documentId` | Versioned document, review decision, evidence drawer and export/download states. | Documents/claims/delivery APIs; review details, reassembly and artifact discovery gaps. |
| Results / Library `/results` | One collection with current deliverables and history filters, search, version/provenance summary; same reader links. | Global document search/pagination gap; do not label a recent subset “all results”. |
| Capabilities `/capabilities` | Only genuinely configured names/purposes and permitted access; explain inactive/unconfigured slots without inventing eight businesses. | Customer-safe catalogue/tool readiness gap. |
| Context and account `/settings/context`, `/settings/account` | Inspect/edit/delete permitted facts; grant/revoke named consent; account session/logout. Show retention limits and external deletion as unconfirmed. | Soul fact/consent writes exist; consent listing, retention/erasure HTTP and account read gaps. |

The operator configuration/recovery surface stays separately permissioned; customer pages must never fetch operator configuration as a shortcut. A future public landing page only explains the same journey and evidence policy; no fabricated testimonials, example customer results or unsupported signup/payment promises.

Create one shared set in the future frontend, following the design contract: `AppShell`, `SidebarNav`, `PageHeader`, `HeroBanner`, `Button`, `SurfaceCard`, `CapabilityCard`, `MissionList`, `StatusBadge`, `EvidenceList`, `EmptyState`, `ErrorState`, `Skeleton`. Add only domain compositions needed above: goal/clarification panel, plan-and-cost review, approval panel, progress timeline, result reader and evidence drawer. Reuse these across MyDash, Missions, Results and Library; keep API adapters separate from presentation. UI state never overrides canonical operation/document state.

Beginners see objective, expected result, cost, current state and next action. Professionals expand scope, tools/permissions, budget provenance, plan dependencies, revision/attempt history and evidence digests on the same screens. Do not add separate “beginner/pro” products or mandatory setup forms.

## 4. UX states and visual acceptance

| State | Required behavior |
|---|---|
| Loading / empty / submission pending | Layout skeleton; purpose-specific empty state; preserve typed input; disable duplicate actions. Never fill with sample missions. |
| `DRAFT` / `READY` | “Draft” / “Plan ready”; clarify or review next. These do not imply approval, available pricing or operational readiness. |
| `RUNNING` / `WAITING_APPROVAL` | Recorded progress / specific decision. Step counts are completed work, not likelihood of business success. A count of approvals is insufficient to authorize anything. |
| `INTERRUPT_REQUESTED` / `INTERRUPTED` | “Stop requested” / confirmed interruption. Explain that in-flight external work may remain unresolved. |
| `FAILED` / `UNKNOWN` / `SUPERSEDED` | Show recorded failure or uncertainty; safe next step and preserved history. `UNKNOWN` is an attempt/outcome state, not a new operation status. `SUPERSEDED` links to the current version. |
| `COMPLETED` / document states | Completion is operation status; only document `DELIVERABLE` receives that label. `DRAFT`, `PARTIAL`, `READY_FOR_REVIEW`, unsupported/stale/conflicting claims and missing citations retain their uncertainty. |
| `PENDING_UPLOAD` / available / expired grant | Pending export is not downloadable; reconcile through the existing service. A successful export returns an artifact ID; the grant endpoint checks `AVAILABLE`. Grants expire after 180 seconds; obtain a new grant without re-exporting. Never embed credentials or persist signed URLs in history. |
| `CONFLICT` / expired approval or quote | Refetch authoritative version/details; preserve user edits for comparison; require review again. No silent approval, stale-plan start or blind replay. |
| Denied / missing resource / expired session | Explain access or reauthentication without exposing another workspace. The API uses `DENIED`/403 for invalid sessions too; do not assume every 403 means session expiry. Clear workspace caches on logout/change. |
| `NOT_CONFIGURED`, `UNSUPPORTED`, payment/budget errors | Persistent reason and next allowed step. Missing permissions, consent, pricing, evidence, isolation or SDK/runtime support blocks the relevant action. Budget exhaustion never silently raises a ceiling. |
| Network error / `UNKNOWN_OUTCOME` | Keep last known data with refresh time. Retry reads with backoff; start/accept reuse their command keys. Do not auto-replay non-idempotent create/export writes or uncertain external actions. |

Use the existing `--qx-*` semantic tokens: deep-navy navigation, cobalt MyDash hero, light canvas/cards, outcome-first mission cards and inspectable evidence. One dominant CTA per screen; no repeated marketing hero on detail pages. Follow the design system's 272px desktop sidebar, responsive drawer, stacked mobile mission rows, 44px touch targets, visible focus, dialog focus handling and WCAG 2.2 AA contrast. EN/FR strings live outside component logic; allow 30% expansion and localize dates/currencies. Use restrained/reduced motion and polite, meaningful progress announcements; no announced timer ticks.

## 5. Contract gaps: prerequisites, not backend rewrite instructions

These are source-reviewed gaps, not newly implemented routes. In a separately authorized integration task, extend the existing boundary/services only where needed; do not recreate commerce, budgets, orchestration, evidence or identity in the client.

| Gap | Required contract / truthful behavior until available |
|---|---|
| Goal → clarification → structured proposal | Soul converse currently requires `operationId` + `attemptId`; Pilot propose also requires a capability and an existing plan revision. Neither supplies a durable clarification thread or validated initial plan proposal. Define authorized pre-execution scope, persistence, consent, cost/limits and a structured proposal mapped to `planCreateSchema`. Saved draft remains usable; automatic planning stays blocked. |
| Mission detail and resumption | `GET /v1/operations/:id` returns `Operation`, not goal text, plan/steps, attempts or full approvals; no customer detail reads expose those aggregates. Define tenant-scoped current/history reads including version, approval purpose/expiry and exact consequential action scope. Never use raw timeline text or operator inspection as authority. |
| Cost, readiness and acceptance reload | Quote creation/acceptance exist; no customer offer catalogue, persisted quote/order read, budget/usage read or estimation endpoint exists. Define safe offer selection, quote/order retrieval and a readiness/budget view backed by existing services, with amounts, currency, expiry, origin and blocking reasons. A user-editable cap needs server enforcement; no cosmetic budget slider. |
| Evidence review to refreshed document | Claims can be assessed, but the normal worker initially records unverified findings and may assemble `PARTIAL`; no HTTP assembly/reassembly command exposes `ResultAssembler.assemble` after assessment. Define the authorized review/reassembly handoff using the existing claim/document services. Do not promise automatic verified delivery or treat an approval as evidence assessment. |
| Complete Library and artifact discovery | Lists are limited (maximum 100 operations) without cursor/search; documents are per operation, with no global result search or artifact metadata list. Define paginated authorized discovery/search and artifact status/IDs so return visits can find prior downloads. Do not fan out across missions to pretend to implement a complete library. |
| Capabilities, privacy and identity | Expose minimal customer-safe capability/tool readiness, consent metadata, authorized account/session context and retention/erasure status through appropriate existing boundaries. Soul context reads filter facts by consent and cannot list all consents. `ContextPolicyService` has no controller; external deletion remains `NOT_CONFIRMED`. Resolve secure client session and same-origin/API transport before authenticated UI integration. |

Deployment blockers remain those in the implementation map: live Hatchet dispatch/observation, Hermes isolation, production storage, public identity hardening, active capability/profile configuration, provider licensing/freshness, and pricing/payment/budget configuration. Isolated QA and a source graph do not certify these. No production dispatch is enabled by this specification.
