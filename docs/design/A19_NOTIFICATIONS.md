## What exists after A19

**Provider code (replacing the not-configured-only stub).** `packages/application/src/email-transports.ts` implements `ResendEmailTransport` (the Resend HTTPS API via `fetch`, 2xx-with-id ⇒ receipt; 429/network ⇒ retryable `EmailDeliveryError`; other 4xx ⇒ permanent) behind the existing `EmailTransport` port, now receipt-returning (`send({to,subject,text,html?,category?,deduplicationKey?})` → `{ providerMessageId }`) with `provider`. `createEmailTransportFromEnv()` selects Resend only when `QEYNOX_EMAIL_PROVIDER=resend` **and** `QEYNOX_RESEND_API_KEY` **and** `QEYNOX_EMAIL_FROM` are all set; otherwise the transport stays `NotConfiguredEmailTransport` and every send fails closed (`NOT_CONFIGURED`, 503, nothing claimed). **Credentials live in deployment secrets only**: `.env.example` documents `QEYNOX_RESEND_API_KEY`/`QEYNOX_EMAIL_FROM` as secrets; nothing reads them from code, logs them, or embeds them.

**Templates.** `packages/application/src/email-templates.ts`: six templates (`EMAIL_VERIFICATION`, `PASSWORD_RESET`, `WORKSPACE_INVITATION`, `APPROVAL_REQUIRED`, `EXECUTION_FAILED`, `RESULT_DELIVERED`) rendered `subject/text/html` in **EN/FR/ES/DE** (reviewed copies, not machine fallback); unknown locales fall back to English (`resolveEmailLocale`); every interpolated value is HTML-escaped.

**Transactional self-service delivery.** Identity verification, password recovery (identity-lifecycle) and workspace invitations (customer self-service and platform organization paths, via the shared `invitation-delivery.ts`) render and send inline, **post-commit**, through the configured transport. The send ledger (`email_deliveries`, migration 0024) records each attempt as SENT/PENDING/FAILED with `attemptCount`, `maxAttempts`, `nextRetryAt`, `lastErrorCode`, `providerMessageId`, `templateId`, `locale`, `deduplicationKey`. Transactional sends carry `attemptCount: 1` and are not retried inline; notification-path deliveries are enqueued PENDING and drained with backoff 60/300/900 s, `maxAttempts` 3, retryable→PENDING, permanent→FAILED, 2xx→SENT. **SENT is recorded only when the provider accepts the message** — never on template render, never on enqueue.

**Notifications.** `NotificationService` (`packages/application/src/notifications.ts`) materializes notification-relevant domain events (`STEPS_COMPLETED_REVIEW_REQUIRED` → APPROVALS / `APPROVAL_REQUIRED`, `STEP_FAILED` and `STEP_OUTCOME_UNKNOWN` → EXECUTION_FAILURES / `EXECUTION_FAILED`, `RESULT_DELIVERED` → RESULTS / `RESULT_DELIVERED`) into inbox rows and delivery jobs. Recipients = operation `createdBy` ∪ active OWNER/ADMIN members (disabled excluded). Preferences (`notification_preferences`) gate e-mail per user per category (default opted in; transactional never opt-out-able); **in-app inbox rows are always recorded**, even when e-mail is opted out. Materialization is idempotent at `(event, recipient)` granularity: the e-mail decision belongs to the first materialization, so re-enabling a category never releases a late mail for an earlier opted-out event. Deduplication keys `evt:<eventId>:<userId>` (inbox + ledger), `identity:<purpose>:<userId>:<tokenId>`, `invitation:<membershipId>` with `onConflictDoNothing`. The worker drains the queue every 5 s; the API exposes `/v1/notifications` (list, `unreadOnly`, cursor pagination), `/v1/notifications/read-all`, `/v1/notifications/:id/read`, `/v1/notifications/preferences` GET/POST. Web inbox at `/{lang}/notifications` (EN/FR copy) shows read/unread, badges and preference toggles.

**Operator-triggered lifecycle sends remain blocked by design** (`ACCOUNT_LIFECYCLE_FLOW_NOT_IMPLEMENTED` when configured, `EMAIL_PROVIDER_*` otherwise) — audited DENIED, no state change, no e-mail. The `capabilities` endpoint reports self-service lifecycle features `AVAILABLE (reason CONFIGURED)` only when a transport is configured, else `BLOCKED` with the real reason.

## Trigger wiring (all through production code, no second path)

`StepProgression.complete()` (last step → `STEPS_COMPLETED_REVIEW_REQUIRED`, inserts the PENDING RESULT_REVIEW approval), `ResultDeliveryService.deliver()` (`RESULT_DELIVERED`, post-commit), and the worker's step failure handling (`STEP_FAILED` / `STEP_OUTCOME_UNKNOWN`, in `apps/worker/src/runtime.ts`) insert the events; the worker drain (`drain(25)` every 5 s) turns them into inbox rows + provider sends. The QA exercises the approval and delivered-result paths end-to-end through the real services.
