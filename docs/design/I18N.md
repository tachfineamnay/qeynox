# Locale and translation architecture

**Status:** EN and FR are the only supported, routable interface locales.
**ES and DE are prepared, not translated.** No ES or DE string ships until a reviewed catalog lands.

## The single registry

`apps/web/src/lib/locales.ts` is the one place that knows which locales exist:

- `SUPPORTED_LOCALES` — locales the router, metadata, sitemap and app shell accept. Today: `en`, `fr`.
- `PENDING_LOCALES` — locales documented as under preparation. Today: `es`, `de`. They are **not**
  routable; `/es/...` and `/de/...` return 404 by design.
- `isSupportedLocale()` — the routing gate used by `app/[lang]/layout.tsx`.

Adding a locale to `SUPPORTED_LOCALES` is necessary but never sufficient: routing, metadata and
the sitemap derive from the registry automatically (see `lib/site.ts`, `app/sitemap.ts`), but every
catalog must be reviewed in the same change.

## Catalogs

All customer-facing copy lives in typed catalogs. The English catalog is the reference shape, and
the French catalog is checked against it at compile time (`const fr: typeof en`), so a missing or
extra key fails `tsc`:

| Catalog | File | Type export |
| --- | --- | --- |
| App shell, workspace, auth, statuses | `lib/copy.ts` | `CopySuite` |
| Public marketing pages | `lib/public-content.ts` | `SiteCopy` (interface) |
| Mission workspace | `lib/mission-copy.ts` | `MissionCopy` |
| Flow workspace | `lib/flow-copy.ts` | `FlowCopy` |
| Soul onboarding | `lib/copy.ts` (`soulCopy`) | — |

Design rules from `docs/design/DESIGN_SYSTEM.md` still apply to every new locale:

- Never hardcode UI copy in component logic.
- Strings must expand by ~30% without clipping; keep date/number/currency formats locale-aware.
- Do not invent copy. Unreviewed machine output is not a translation.

## Adding ES or DE (or any future locale)

1. Copy the `en` object in each catalog and translate it as **one reviewed unit** — never
   key-by-key over time, never with unreviewed machine output.
2. Type the new catalog against the reference (`const es: typeof en`), which forces completeness.
3. Register the locale in `SUPPORTED_LOCALES` in `lib/locales.ts`.
4. Add `es`/`de` entries to any catalog keyed by `Record<Locale, ...>` that the compiler flags
   (the type system enumerates them), e.g. `legalPlaceholders`, `publicCopy`, `soulCopy`,
   `supportCopy`, `missionCopy`, `flowCopy`.
5. Routing, hreflang (`lib/site.ts`) and the sitemap (`app/sitemap.ts`) pick the locale up
   automatically from the registry.
6. Verify: both locales at 390/1024/1440, full keyboard pass, ~30% expansion spot checks, the
   screenshot set regenerated, and a reviewer sign-off recorded in the PR.
7. `PENDING_LOCALES` entries are removed as locales are promoted to `SUPPORTED_LOCALES`.

## Fallback policy

There is no silent per-key fallback to English. An unfinished catalog is unshippable — the compile
error is the guard. If a locale must be withdrawn, remove it from `SUPPORTED_LOCALES`; its routes
404, its metadata and sitemap entries disappear with it.

## What is intentionally not done

- No ES/DE strings, placeholders or machine-translated copies exist in the repository.
- Backend-driven business states (statuses, readiness, commercial states) are not localized by the
  web layer beyond the existing `statuses` catalog; they must never be re-interpreted per locale.
