# ADR-022 — The first operational business service (World Bank economic research)

- **Status:** Accepted
- **Date:** 2026-11-19
- **Mission:** A03
- **Supersedes nothing.** Builds on ADR-012 (connectors), ADR-013 (claims), ADR-014 (results),
  ADR-016 (bounded agency) and ADR-020 (runtime readiness).

## Context

QeyNox could already execute a research plan end to end — `qa-raas-deliverable.ts` proves
configuration → plan → quote → provider read → evidence → review → deliverable. What it lacked was a
**product**: a service a customer can invoke with an explicit objective, a configuration an operator
can reuse, and a validation path that fails before a customer discovers a defect mid-operation.

The operator configuration that was supposed to define that service,
`infra/operator/mission10-economic-research.json`, contained defects that would have shipped a
service that could not work correctly. This ADR records the repairs and the design of the service.

## Decision 1 — configuration is validated, never assumed

`validateServiceConfiguration()` reports every finding with a stable code and a remedy, and returns
`valid: false` if any finding is a BLOCKER. It is read-only: a repair is an operator edit, never an
automatic mutation.

Blockers found in the mission-10 file and repaired in `infra/operator/a03-economic-research.json`:

| Defect | Consequence if unshipped | Repair |
| --- | --- | --- |
| `BUDGET maxMoneyMinor=500`, engine rate `40`, profile `maxIterations=4` | The ceiling affords 12 engine calls in total but is shared with retries; a plan retried three times starves mid-flow. | `maxMoneyMinor=4000`, `maxAgentCalls=24` |
| `VERIFICATION humanReviewRequired=false` | An agent finding could look promotable; the mission requires review before SUPPORTED. | `humanReviewRequired=true` |
| `VERIFICATION maxAgeDays=365` | A year-old economic observation could support a "current" claim. | `maxAgeDays=180` |
| `OFFER regions=['FR','BE']` | Looked like a provider limit; the provider is global and the capability has no regional bound. | `regions=['GLOBAL']` |
| No country/indicator allowlist | Any well-formed code was accepted, so the "reviewed scope" was undefined. | Explicit `allowedCountries` / `allowedIndicators` |
| Registry `world-bank` `INACTIVE` while the mission declared it ACTIVE | Two sources of truth disagreeing about whether egress is permitted. | Registry reconciled to the reviewed adapter state |

`humanReviewRequired:false` is deliberately only a **WARNING**. `ClaimsService.assess` promotes a
claim to `SUPPORTED` only through an authorized reviewer decision, so the omission is a clarity
defect, not an authorization bypass — and the validator proves the claim path still enforces review.

## Decision 2 — the request is explicit and bounded

The service accepts `{ objective, country, indicator, constraints }`. Nothing in that object is
generated by a model.

- `objective` is required, 20–5 000 characters, and is the customer's own words.
- `country` must match ISO 3166-1 alpha-2/alpha-3; `indicator` must be a dotted World Bank code.
- When an operator allowlist exists, the request may only choose *inside* it. A well-formed but
  unreviewed code is `DENIED`, not silently accepted.
- `constraints` are bounded: `mostRecent` 1–5, `minObservationYear` 1960..current, at most two
  `compareIndicators` that must not repeat the primary, `note` ≤500 characters.

The normalized request carries a **fingerprint** (a deterministic digest over every field in a fixed
order, no timestamps). The user approves a specific scope; changing interpretation mode or adding a
comparison changes the fingerprint.

The plan is derived deterministically: one `RESEARCH` step, plus one dependent `ANALYZE` step when
interpretation is requested. A request that exceeds the capability's `maximumToolCalls` or
`maximumSteps` is **refused**, never truncated — silently dropping a comparison would deliver a
different service than the one that was approved.

## Decision 3 — the provider is only ever the reviewed adapter

Every observation comes from `world-bank:indicator@1` through `ToolBroker`. The profile allows no
other tool, so an unrestricted model web request is not expressible in this configuration. The
broker still enforces the full contract: capability membership, profile version, consent scopes,
budget units, and an idempotent ledger reservation.

`Provenance.publishedAt` is **undefined** for this provider — the World Bank API reports no
publication date. The claim assessment therefore records "publication freshness unknown" and the
retrieval time is the only freshness signal. That limitation is surfaced rather than hidden.

## Decision 4 — evidence is digest-bound and review is human

A support link must cite the exact captured response digest; `ClaimsService.attach` rejects a link
without evidence and rejects a forged digest. Structural eligibility never promotes a claim:
`maximumSources: 1` produces `NEEDS_HUMAN_REVIEW`, and only an `OWNER`/`ADMIN`/`REVIEWER` decision
with a rationale produces `SUPPORTED` (`method: HUMAN_REVIEW`).

## Decision 5 — what "operational" means, and what was not proven

The service is `OPERATIONAL` only when configuration is present, the provider is enabled, and the
runtime (engine + orchestrator) is attested live — the A01 four-state model. Anything less is
`BLOCKED`, `UNVERIFIED` or `CONFIGURED`.

This mission separates two kinds of evidence:

1. **Verified in isolation.** Configuration validation, the request contract, the bounded plan, and
   — against a disposable PostgreSQL 16.2 cluster — tenancy isolation, budget materialization and
   exhaustion, and the broker's refusal of a tool outside the capability.
2. **BLOCKED.** The live World Bank read. This environment resolves `api.worldbank.org` but the TLS
   connection is refused by network policy, so the provider leg, its provenance, human review and
   the deliverable were **not exercised**. The QA exits **3 (BLOCKED)** and substitutes no fixture.

Anyone running this on a host with provider egress gets the full chain from the same command; the
exit code tells them which result they got.

## Consequences

- A second service copies `infra/operator/SERVICE_TEMPLATE.md` and supplies its own reviewed codes.
- `pnpm qa:a03-service` is the gate: exit 0 means definition **and** integration passed; exit 3 means
  definition passed and the provider leg is unproven. Exit 3 must never be reported as a pass.
- The allowlist is the product scope. Adding an indicator is an operator decision with a licence and
  review obligation, not a code change.
